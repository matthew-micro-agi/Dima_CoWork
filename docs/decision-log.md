# Decision Log

Choices, alternatives, reasons and dead ends for the firmware trial. Each entry says what we decided, why, what else we considered, and what may need enhancing later. The log is meant to be readable on its own.

**Context in brief.** We build a recording node for a rig of hardware-synchronised cameras: each camera has its own node that encodes H.265 in hardware and records to its own eMMC as a ring of short segment files. A hardware trigger starts every frame; every frame carries the index of the trigger edge that started it. A controller runs many nodes over Ethernet. The bench is a TI J722S evaluation board (EVM) running TI's Linux SDK image; product nodes come later in two tiers (a TI-based standard tier and a cheaper Rockchip-based "lite" tier with a small supervisor microcontroller). The original system description (the "Architecture Context") was written by the hiring team; where we deviate from it, the entry says so.

All dates 2026-11-12.

## DL-01 Time sync: PTP (gPTP)

**Decision.** Nodes keep their hardware clocks synchronised with the **Precision Time Protocol (PTP, IEEE 1588), in the gPTP profile (IEEE 802.1AS)**, using the standard Linux tools `ptp4l` and `phc2sys` (linuxptp). Within a group of about ten cameras ("pack"), one wired electrical edge triggers all sensors. Between packs, each pack generates its own edge from PTP time. This follows the original system description.

**Why.**
- Uses the Ethernet the system needs anyway; no extra cabling between packs.
- The industry standard for "many devices on one Ethernet, microsecond-level sync" (time-sensitive networking, automotive, broadcast, telecom).
- Our hardware supports it: the board's Ethernet controller timestamps packets in hardware. **Measured on the bench: 30 ns RMS, 85 ns maximum offset** between the board and the laptop over a direct cable.
- Matches the planned controller (a Microchip LAN9668 TSN switch; Zephyr has a gPTP stack).
- `ptp4l` is the reference Linux implementation; a few hundred nodes per network is ordinary for it.

**Alternatives considered.**

| Alternative | Typical accuracy | Why not (now) |
|---|---|---|
| NTP with hardware timestamps (`chrony`) | ~1-10 µs on a quiet LAN | no help from switches, worse under video load; not used in time-sensitive networking. Possible fallback. |
| Wired sync line across packs (RS-485/LVDS) | ns | extra cabling, doesn't scale without limit, carries no time of day. Kept **within** a pack. |
| IRIG-B timecode + pulse-per-second | ~µs | separate cable, dated tooling, no advantage over PTP |
| GNSS receiver per node | 20-50 ns to UTC | needs sky view; the device is head-mounted and indoors |
| White Rabbit (CERN's PTP extension) | sub-ns | special switches and fibre; accuracy we don't need |
| Synchronous Ethernet | frequency only | a supplement to PTP, not a replacement |
| EtherCAT distributed clocks | ~100 ns | its own industrial fieldbus; doesn't carry our video and control |
| Radio time transfer (Nordic 2.4 GHz, UWB, Wi-Fi timing) | µs or better, varies | unproven for us; relevant only to a possible cable-free lite tier |

**Requirements when scaling to ~100 nodes.**
- **Time-aware switches** in every hop (transparent or boundary clocks, or 802.1AS bridges). Plain switches add microseconds to milliseconds of queuing noise under video load.
- **One gPTP configuration** on all nodes, shipped in our image. (The bench check used linuxptp's default settings, not yet gPTP.)
- **A proper grandmaster clock** (good oscillator, UTC from GNSS or NTP) with defined failover and holdover.
- **Per-node monitoring**: PTP state and offset reported in node health, with alarms.
- **Qualify every network card and driver** with an offset/jitter test. Lesson from the bench: the laptop's Intel I219 hardware clock ran ~1600 ppm (0.16 %) off and works as PTP master only while `phc2sys` corrects it against the NTP-synced system clock.
- Matched cable lengths within a pack; absolute accuracy calibrated once per hardware type against a pulse-per-second reference and an oscilloscope. (PTP cannot see delays that differ between the two directions; the bench measurement shows stability, not absolute accuracy.)

**Possible enhancements later.**
- *Security:* a closed network with switch port roles (only the grandmaster's port may announce itself as master; nodes run "slave only") as the baseline; PTP message authentication (IEEE 1588-2019 security annex, supported by linuxptp) or MACsec link encryption if the threat model needs it (check support in Zephyr and the switch first); authenticated NTP (NTS) for the grandmaster's UTC source; alarms on sudden path-delay changes (delay attacks can be detected but not prevented by cryptography).
- *Low power:* Single Pair Ethernet (10BASE-T1L) for links that carry only sync and control; Energy-Efficient Ethernet switched off on PTP links (it adds variable latency); a temperature-compensated oscillator (TCXO) for holdover; radio time transfer for the lite tier. Time sync itself is negligible next to the roughly 1-2 W of a recording node (estimate); the physical link dominates.

## DL-02 Language for code on the node: C

**Decision.** All our code that runs on the node is C: the trigger daemon, the capture/recorder process and the control-interface server.

**Why.** Our code sits in the data path; GStreamer's native API is C; the TI SDK's cross-compiler is ready to use; C keeps the footprint small, which also suits the lite tier (Rockchip RV1106: one Cortex-A7 core, 128-256 MB RAM). The HTTP library we need (`libmicrohttpd`) is already in the SDK and on the board image.

**Alternatives.**
- **Rust:** probably the right long-term choice (memory safety, official GStreamer plugin support), but setting up its cross-toolchain against the SDK takes too long for a prototype. Kept as the product option.
- **Python:** rejected for the node. Slower, less control, far more CPU and memory than firmware should spend.

Tools that run only on the laptop (tests, debugging) are not firmware; their language is decided separately.

## DL-03 Control-interface encoding: CBOR + CDDL + zcbor

**Decision.** Messages between the controller and a node are encoded as **CBOR** (Concise Binary Object Representation, RFC 8949). The message definitions are written in **CDDL** (RFC 8610), one file per interface version; that file is the contract. C encode/decode code is generated from it by **zcbor**. The node speaks CBOR only.

**Why.** An IETF standard; works on both the Linux node and the Zephyr microcontrollers (controller, supervisor); built into Zephyr (its device-management protocol and bootloader use it); pairs with CoAP; maps one-to-one to JSON, so humans can read it with a converter; self-describing (readable without the schema).

**Alternatives.**
- **Protocol Buffers (nanopb):** equally common in small firmware, with generated code and clear evolution rules. Not self-describing, and less aligned with Zephyr and CoAP.
- **JSON on the node:** rejected. Larger, slower to parse, a second code path to test.
- **MessagePack:** rejected. No standard schema language, weak for conformance testing.
- **FlatBuffers:** rejected. Overkill for a few kilobits per second of control traffic.
- **Raw C structs or hand-made TLV:** rejected for this interface. Not portable between independent implementations (byte order, padding, fragile versioning).

The TI SDK has neither CBOR nor protobuf libraries, so the SDK did not decide it: the library is bundled in our repository either way.

**Dead end.** zcbor 0.9.1 requires "cbor2 5.4.2 or newer" with no upper limit; pip installed cbor2 6.2.1, which removed a class zcbor imports, so zcbor failed to start. Fixed by pinning cbor2 below 6 (5.9.0) in `tools-requirements.txt`.

## DL-04 Control-interface transport: HTTP now, CoAP later

**Decision.** For the trial the node serves the control interface over **HTTP** (library `libmicrohttpd`), with a version in every path (`/v1/…`). Recorded video is fetched by the PC directly from the node with HTTP range requests. Events from node to controller: Server-Sent Events carrying CBOR (to be confirmed). For the product, **CoAP** replaces HTTP for control and events, with the same CBOR messages. **JSON exists only on the laptop**, as a human-readable view produced by a converter.

**Why.** HTTP is easy to test and already available on the board. CoAP suits a microcontroller-based controller. Keeping JSON off the node keeps the firmware small (one encode/decode path).

**Alternatives.** A node serving both CBOR and JSON (rejected: an extra library and code path); gRPC (rejected: not available on Zephyr, heavy for a microcontroller); MQTT (rejected for now: needs a broker, which the small controller can't host).

**Deviation from the original description.** The original description had the controller collect video and forward it to a PC. We have the PC fetch directly from the nodes, because a small microcontroller-based controller cannot forward ~100 Mbps; its load stays limited to control traffic.

## DL-05 Build system: CMake

**Decision.** CMake, with a toolchain file (`cmake/j722s-sdk.cmake`) that points at the TI SDK's cross-compiler and target filesystem.

**Why.** One code base, two builds: on the laptop for unit tests, and cross-compiled for the board. CMake finds GStreamer and libmicrohttpd in the SDK via pkg-config, regenerates the zcbor code when the CDDL changes, runs tests with `ctest`, and is supported by Yocto for a later product image. Already installed on the laptop.

**Alternatives.** Plain Make (simpler, but two targets plus pkg-config plus code generation plus tests become messy); Meson (GStreamer's own build system, attractive for our future GStreamer elements, but not installed, and CMake builds GStreamer plugins too).

## DL-06 Segment index: append-only manifest, no database

**Decision.** Each node keeps a file `manifest.bin` on its eMMC: one small record per segment file (session, first and last frame index, times, size, keyframe positions, flags), only ever appended to. It is the source of truth. The recorder process loads it into memory at start and is its **only owner**; the control-interface server asks the recorder over a local socket instead of reading the file itself.

**Why.** Writes are simple: one append every 4 seconds, and deletions are recorded before the file is removed. After a crash only the last few records need checking. Queries are few and fixed (by session, by frame range, by time range), so a binary search in memory is optimal: about 15 steps for 24 hours of recording.

**Alternative: a lightweight database (SQLite), rejected.**
- There are no multi-record transactions to protect.
- Access from several processes is covered by having a single owner.
- A database costs what an embedded recorder should not spend: several times more eMMC writes (write-ahead log, page writes, checkpoints), several hundred KB of library plus SQL parsing, checkpoints at times we don't control, and one more dependency.
- Reconsider only if the node must store rich metadata with many kinds of queries, or gets several independent writers.

## DL-07 Segment length: 4 s

**Decision.** Recordings are split into 4-second segment files; a keyframe every second (1 or 2 s still to be confirmed); every segment starts with a keyframe and decodes on its own.

**Why.** A power of two; a whole number of frames at both frame rates (120 at 30 fps, 240 at 60 fps), so segment boundaries fall exactly on trigger indices; about 2.5 MB at 1080p30 and 5 MB at 1080p60 (under 10 MB); inside the 1-10 s range of the original description.

**Alternatives.** 5 s (first proposal, no strong reason); 10 s (fewer files, but coarser locking and older data when fetching). The advantages of shorter segments (fresher data, less loss on a crash) are covered separately: the recorder flushes to eMMC at every keyframe and can serve the segment still being written.

## DL-08 Media framework: GStreamer

**Decision.** GStreamer for capture, image processing and encoding. Now: a thin pipeline with our code at its input (`appsrc`) and output (`appsink`). Later: the same logic wrapped as our own GStreamer elements, so the whole node is one portable pipeline.

**Why.** TI's image signal processor is in practice only reachable through TI's GStreamer elements; encoder, capture and test sources come ready-made; GStreamer is the industry standard and portable (on Rockchip only the encoder element changes). Our logic is written as plain functions so it can be wrapped as elements without rewriting.

**Alternative.** Plain V4L2 calls in C: more control and less overhead for the encoder, but no way to reach the image signal processor.

**Dead ends (encoder bench test).** GStreamer's built-in test source draws frames in software (10-40 fps at one full CPU core), so our first encoder test measured the test source, not the encoder; the encoder's rate control is off by default and must be enabled or the bitrate setting is ignored; a raw-frame source must declare its colour space (`colorimetry=bt709`) or the encoder refuses it; the `identity eos-after` element does not stop at an exact frame count.

## DL-09 Timestamping our own trigger edges: device-tree overlay

**Decision.** The board's PTP hardware can generate the trigger edges (a "periodic output") and timestamp external edges (an "external timestamp input"). To timestamp our own edges, the periodic output must be routed internally to a timestamp input through the SoC's "timesync router". We do this with a **device-tree overlay**: a small file loaded by the bootloader on top of TI's unmodified device tree, which adds the router and the route (periodic output 1 -> timestamp input 3). Source: `dts/k3-j722s-evm-fwtrial-cpts-loop.dtso`. **Not deployed yet.** Until it is, the trigger daemon computes edge times from the schedule instead of measuring them (see DL-13).

**How we got here.** On the bench the periodic output ran, but no timestamps arrived. The board's TI 11.0 device tree has no router configured; the route exists only in the newer 11.02 SDK. The board's kernel supports the overlay.

**Alternatives.**
- Decompile the running device tree, edit it and boot it: rejected. It bakes in changes the bootloader makes at boot time, loses readable names, and replaces TI's reference tree.
- Move to the 11.02 SDK's kernel and device tree: rejected for now. A much larger change; revisit when we need kernel or driver work.
- A physical wire from an output pin to an input pin: rejected. A board modification, and it needs pin-configuration overlays anyway.

**Enhancement needed later.** Deploy the overlay and switch the trigger daemon to measured timestamps; that is what proves each edge fired and gives jitter numbers.

## DL-10 Camera for the trial

**Decision.** For the trial, prefer a camera **whose driver already exists in the TI SDK**; among those, **support for an external trigger** decides. Without trigger support, the trigger chain is proven up to the connector pin using a test source, and the gap is stated. The product sensor's (onsemi AR0235) driver and image tuning are our own work and a later milestone. The trial starts without a camera, using a trigger-driven test source.

**Why.** An existing driver turns days of driver work into configuration; the hardware trigger is the property the whole product depends on, so it decides between supported cameras.

## DL-11 Trigger daemon -> consumers: datagram socket, versioned struct, subscription

**Decision.** The trigger daemon (`trigd`) publishes one message per trigger edge over a **Unix datagram socket** on the node. The message is a **versioned C struct**: version, session, edge index, edge time in nanoseconds, flags. Consumers **subscribe** by sending a subscribe message to `trigd`'s socket; `trigd` sends every edge to every subscriber.

**Why a datagram socket.** 30-60 messages per second is trivial for a socket; it is simple, needs no library, and is easy to replace later (for example with shared memory) without touching the message content.

**Why a C struct here, when the control interface uses CBOR.** This is internal communication between our own programs on the same board, built together from the same source. The control interface is a contract between independently written implementations (Linux node, Zephyr controller), where a portable, schema-checked encoding matters. A version field in the struct still allows changes.

**Why subscription from the start.** One consumer (the capture process) is enough today, but three realistic cases need more, and supporting them later would mean changing `trigd`:
- several cameras per node, each with its own capture process (the J722S has four camera connectors and one edge can trigger all of them);
- recording the camera module's motion sensor (IMU) aligned to the same edges;
- attaching a diagnostic listener to a running node without stopping capture.
The cost now is a few dozen lines.

**Possible enhancements later.** Shared memory instead of a socket, if rates ever become high; CBOR for this message too, if consumers are ever built separately.

## DL-12 Session plan delivery and start time

**Decision.** A recording session is defined by a **session plan**: session number, start time of edge 0 (T0, on the PTP clock) and period between edges. In the product, the control-interface server receives the plan from the controller and passes it to `trigd` over a **local Unix control socket**. In the first version (no control-interface server yet), `trigd` takes the plan from its **command-line arguments**, using the same plan structure.

**Start time.** T0 is always in the future, so that the moment a command arrives (which varies by milliseconds across nodes) doesn't matter: every node's hardware fires the first edge at exactly T0. Default when no T0 is given: **the next whole second on the PTP clock plus 1 second**. The offset is configurable, and an explicit T0 can be given (which is what the controller will do).

**Why.** One plan structure for both paths means the first version's code is the product's code; only where the plan comes from changes. Rounding to a whole second makes logs easy to read; one second of margin leaves time to arm.

## DL-13 When the clock is not verified as synchronised

**Problem.** `trigd` computes edge times from the board's PTP clock. They are only comparable across nodes if that clock is synchronised with the others. If it is not (PTP not running, not yet locked, lost during a session), each node is still consistent with itself, but the same edge index on two nodes no longer means the same instant, and nothing would notice. A worse case: if PTP corrects a large error by **jumping** the clock during a session, the edge schedule jumps with it.

**Decision for the first version.** **Arm anyway and mark the data.** Every edge message carries a flag "time not verified". The first version cannot yet check PTP's state, so it **sets this flag on every edge**. The data stays honest, and the bench is never blocked.

**Planned enhancement (product).** This approach will need extending:
- `trigd` asks `ptp4l` for its state (through `ptp4l`'s local management socket) and **clears the flag only while the clock is locked** with a small offset;
- **refuse to start a session while the clock is not locked**;
- **during a session, flag the affected edges and raise an event** when lock is lost or the clock jumps;
- configure `ptp4l` to **never jump the clock after the first lock**, only adjust its rate, which removes mid-session jumps at the source.

Because the flag is in the message format from the start, these enhancements change only `trigd`, not its consumers.
