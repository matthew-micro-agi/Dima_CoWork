P-2 CPTS loop sanity (testptp)                     [done 2026-11-12, gap found; closed 2026-11-13]
    Why:  find which Linux perout index = GENF1 and which extts index = HW3_TS_PUSH,
          and that the loop delivers timestamps at the set rate. trigd depends on it.
    How:  ~/fwtrial/prereq/p2-cpts/build.sh cross-compiles testptp.c straight from the SDK
          kernel tree (not copied; GPL), using the kernel's own UAPI ptp_clock.h (the
          sysroot's is older: no PTP_MASK_* ioctls). Binary copied to the board /tmp.
            /tmp/testptp -d /dev/ptp0 -c                  capabilities
            /tmp/testptp -d /dev/ptp0 -i 1 -p 33333333    periodic output 1 @ 30 Hz
            timeout 3 /tmp/testptp -d /dev/ptp0 -i N -e 5 read 5 events, N = 0..3
            /tmp/testptp -d /dev/ptp0 -i 1 -p 0           output off
    Results:
      Capabilities  2 periodic outputs, 4 external timestamp channels, 0 PPS,
                    0 programmable pins, max freq adjust 488281 ppb
      CPTS clock    500 MHz (dmesg: "CPTS ... freq:500000000 ... pps:0") -> 2 ns resolution
      PHC time      ~4250 s (1970): free-running from boot, nothing syncs it yet (P-3)
      Perout        request OK; it is NOT stopped when the fd closes (ptp_release only
                    frees the event queue) -> trigd must disable the output explicitly
      Extts 0..3    NO events on any input within 3 s
    Cause (live device tree of the 11.0 image):
      - CPTS node has no "ti,pps"; timesync router (mux-controller@a40000) node is absent.
      - The GENF1 -> HW3_TS_PUSH loop exists only in the 11.02 SDK EVM tree
        (ti,pps = <2 1>, timesync router: K3_TS_OFFSET(12, 0x0001ffff, 17)).
      - So on the current image nothing routes an output back into a timestamp input.
    Fix chosen (gap, not a blocker): a device-tree overlay that adds the timesync router
      with mux-reg-masks-state = <0x34 0x0001ffff 0x10011> (output 12 = HW3_TS_PUSH <-
      input 17 = GENF1), without ti,pps (so trigd owns GENF1). Checked prerequisites:
      CONFIG_MUX_MMIO=y, TI's "mux-reg-masks-state" extension present in the board kernel
      Image, bus label cbass_main exists, bus cells 2/2, overlays load from /boot/dtb/ti/
      via name_overlays in uEnv.txt, dtc in the SDK.
      Source: ~/fwtrial/dts/k3-j722s-evm-fwtrial-cpts-loop.dtso. NOT deployed.
    Until then: trigd runs in computed-time mode (t_k = T0 + k*period); M4 jitter and
      edge-fired proof need the overlay (measured mode).
    Closed 2026-11-13 (setup.md 7): overlay deployed via name_overlays (backup
      uEnv.txt.pre-g1), router node in the live tree (status okay, driver mmio-mux).
      testptp: output 1 at 60 Hz -> events on input 2 every 16.666666 ms, +8..+14 ns
      from the nominal edge time. trigd --edges auto now measured (see M4).
    Dead end: find on the board does not follow the /proc/device-tree symlink; read
      /sys/firmware/devicetree/base instead.

P-3 PTP link sanity (ptp4l)                                  [done 2026-11-12, passed]
    Why:  hardware timestamping end to end over the direct cable; rough offset.
    Setup: default 1588 settings, layer 2 (-2), NOT yet the gPTP profile.
      laptop (sudo):  ptp4l -i enp0s31f6 -2 -m --tx_timestamp_timeout=50       (master)
      board:          timeout 120 ptp4l -i eth0 -2 -s -m > /tmp/p3_ptp4l.log    (slave only)
    Run 1 (laptop ptp4l only)                                         FAILED
      board reached SLAVE, but master offset grew ~1.05 ms/s (2.8 ms -> 116 ms in ~110 s),
      board freq pinned at +488281 ppb (its max), path delay NEGATIVE (-200..-630 us).
    Diagnosis: each hardware clock vs its own NTP-synced system clock, 10 s apart
      board:  /tmp/testptp -d /dev/ptp0 -k 1  -> +5.41 ms/10 s = ~540 ppm, of which +488 ppm
              was ptp4l's leftover correction -> native ~50 ppm (normal crystal)
      laptop: sudo phc_ctl enp0s31f6 cmp      -> +15.95 ms/10 s = ~1600 ppm (!)
      -> the laptop's Intel I219 hardware clock runs ~1600 ppm off (likely driver assumes the
         wrong crystal frequency). See 0000 P10.
    Fix: discipline the laptop clock to its system clock (sudo, keep running):
      phc2sys -s CLOCK_REALTIME -c enp0s31f6 -O 0 -m
      -> freq -1,599,5xx ppb accepted by the driver, offset within ~±50 ns.
      Board freq reset before run 2: /tmp/testptp -d /dev/ptp0 -f 0
    Run 2 (laptop phc2sys + ptp4l)                                    PASSED
      LISTENING -> UNCALIBRATED -> SLAVE in ~3 s
      last 60 s: offset RMS 30 ns, max |offset| 85 ns
      board freq -56.8 ppm (stable) = board crystal error
      path delay +7.49 us (stable; large for one cable -> likely NIC-internal latency on the laptop)
    Not measured: absolute accuracy (asymmetric delay invisible to PTP; needs PPS + scope).
    Notes:
      - ptp4l's frequency correction stays applied after ptp4l exits (reset with testptp -f 0).
      - phc2sys -O 0 makes PTP time = UTC, not TAI (gPTP expects TAI) -> fix with gPTP config (A11).
      - Board PHC now on UTC, free-running with -56.8 ppm applied; full log in board /tmp/p3_ptp4l.log.

M4  Trigger interval jitter (CPTS)          [done 2026-11-13: exact unlocked; DRIFT with PTP locked]
    Why:  the core timing claim; edges from hardware, not software.
    How:  trigd arms GENF at 30/60 Hz, reads HW_TS_PUSH timestamps (GENF1 -> HW3_TS_PUSH
          loop on the EVM); histogram of edge-to-edge intervals over 30+ min.
    Later: logic analyzer on the trigger pin (J1 pin 18) to confirm at the connector.
    How (now): tests/trigd-check.sh dev root@10.42.0.132 (trig-listen: interval - period
          min/max/RMS + histogram, trigd: measured vs plan); by hand:
            /tmp/trigd --session N --fps 60 --count 600 & /tmp/trig-listen -q
    Results (board, PTP free-running, 300-600 edges):
      60 fps       600/600 edges measured, 0 without timestamp; every interval = period
                   (0 ns, all within the 2 ns resolution); constant +14 ns from T0 + k*P
      30 fps       FOUND: interval = period - 1 ns on every edge (300/300) -> edges drift
                   off the plan by 30 ppb (54 us per 30 min). Cause: the CPTS makes whole
                   2 ns ticks; 33,333,333 ns is odd. Fix: periods in whole ticks (30 fps =
                   33,333,334 ns). After: every interval = period (0 ns), 300/300.
      Fallback     --extts 3 (no loop there): WARNING after 3 edges, computed times, 0 gaps
    30 min with PTP locked (soak 2, M13): FOUND (gap G4): edges do NOT follow ptp4l's
          frequency correction. Every captured interval ~950 ns long (57 ppm at 60 fps;
          PHC freq correction -52..-58 ppm); edges drift off T0 + k*P by 57 us/s.
          trigd: published 108,001 = measured 54,405 + TS_MISSING 53,596; events ignored
          53,590 (beyond a quarter period off the plan); max 4.17 ms off the plan.
          trig-listen: interval - period: half <= 2 ns (TS_MISSING edges = plan), half
          <= 1 us (max +976 ns), 12 > 10 us.
    Cause (driver source, am65-cpts.c am65_cpts_ptp_adjfine): the frequency correction
          goes to the time counter and only to the GENF used as the kernel's PPS
          (ti,pps); a PEROUT-requested GENF gets ppm 0 and is never updated. Our overlay
          has no ti,pps (trigd owns GENF1) -> GENF1 runs at the crystal rate.
          Before G1 (computed mode) the same drift existed with PTP locked, unseen.
    Fix (planned, architecture 11.2 step 1): apply the correction to every enabled
          GENF in adjfine (driver patch, module for the board's kernel); then repeat
          this 30-min run with PTP locked. Pin-level with a logic analyzer.

M11 Binding by time with the camera emulator                  [done 2026-11-13]
    Why:  a camera delivers frames on its own clock; the index must come from the trigger
          edge by timing alone (DL-27), never from counting frames. No camera yet (0000 P7):
          cam-emu plays a triggered sensor and draws the true index into every frame.
    How:  tests/camemu-check.sh dev root@10.42.0.132   (host: tests/camemu-check.sh host)
          trigd (PTP clock) + cam-emu + nodecap --src emu, Wave5, 1920x1200, 60 fps,
          600 edges; streams checked on the laptop with sei-dump (drawn index = SEI index).
          By hand: docs/setup.md 8.3 "Camera emulator".
    Results (board):
      Clean        600/600 bound, 600 pictures, no gaps, pixels ok
      Latency      measured 24.50-25.50 ms (configured 25 +- 0.5 jitter) -> conversion
                   PTP -> monotonic adds no visible error
      Faults       3 % drop/extra/late, 2 % sequence jump (seed 11): dropped 18, extra 23,
                   late 12, jumps 10 -> nodecap: 30 edges without frame (= 18 + 12),
                   35 spurious (= 23 + 12), 10 sequence jumps, 0 frames with a wrong index
      Emulator     max delivery lag 3.4-3.8 ms after the frame's timestamp (< 16.7 ms period)
    Found on the way:
      Window       +- half period (8.3 ms at 60 fps) and +- 5 ms: 1 frame got the wrong index
                   (a 3/4-period-late frame took the next edge whose own frame was dropped);
                   +- 3 ms: none. Default now 3 ms, refused at >= 1/4 period (DL-27).
      Render cost  one noisy 1920x1200 frame takes 19.6 ms on the A53 (> 16.7 ms period at
                   60 fps): the emulator fell behind, frames arrived after nodecap had
                   decided their edges (1 of 600 bound). Fix: 8 frames rendered once at
                   start, then copied (a copy is what a camera's DMA costs).
      First touch  first 4 frames delivered 8.8-14.2 ms late: the kernel allocating the
                   shared buffers on first write (~850 pages each). Fix: buffers touched at
                   allocation, as a driver does. Max lag then 3.4 ms.
      Laptop       x265 can't keep up with noisy frames at 60 fps (drops in the encoder,
                   binding still 600/600) -> laptop checks at 30 fps.
    Limits: the emulator's latency is fixed; a real sensor's timestamp moves with exposure
          time and has interrupt jitter -> measure the spread on the camera before setting the
          window; sensor frame counter as second signal before a real camera is trusted
          (DL-27 Later).
